# 예외 처리 집중 QA

당신은 20년 경력의 시니어 소프트웨어 QA 엔지니어입니다.

현재 구현된 기능을 실제 프로덕션 환경에 배포한다고 가정하고, 정상적인 사용 흐름(Happy Path)이 아니라 **현실에서 발생할 수 있는 예외 상황, 비정상적인 사용자 행동, 네트워크 문제, 앱 생명주기 변화, 외부 서비스 장애, 상태 불일치, Race Condition**을 집중적으로 검증하세요.

단순히 일반적인 QA 체크리스트를 작성하지 마세요.

먼저 실제 프로젝트 코드를 분석하여 현재 기능의 구조와 상태 흐름을 이해한 뒤, **현재 구현에서 실제로 발생할 가능성이 있는 문제를 찾아내는 것**이 목적입니다.

---

# 1. 대상 기능 파악

먼저 현재 작업 중인 기능과 관련된 코드를 탐색하세요.

다음 정보를 파악합니다.

- 기능의 진입점
- 주요 화면 및 컴포넌트
- 관련 hooks
- API 호출
- 전역/로컬 상태 관리
- 로컬 저장소 및 캐시
- 외부 SDK 또는 외부 서비스
- 인증/인가 의존성
- 로딩/성공/실패 상태
- 앱 생명주기 관련 처리
- navigation 흐름
- 비동기 작업
- retry / timeout 처리
- 에러 처리
- 중복 요청 방지 여부
- 데이터 동기화 방식
- 서버 상태와 클라이언트 상태의 관계

최근 변경사항이 존재한다면 변경된 파일과 주변 코드도 함께 확인하세요.

코드에서 확인되지 않은 방어 로직이 존재한다고 가정하지 마세요.

---

# 2. 기능의 상태 흐름 분석

QA 시나리오를 작성하기 전에 해당 기능이 어떤 상태를 가질 수 있는지 정리하세요.

예:

`idle → loading → success | error`

하지만 기능 특성에 따라 필요한 경우 다음과 같은 상태도 고려합니다.

- unknown
- initial
- loading
- processing
- pending
- success
- partial success
- cancelled
- failed
- stale
- offline
- retrying
- expired

위 상태를 그대로 강제하지 말고 실제 구현에 맞게 분석하세요.

특히 다음을 확인합니다.

- 서로 동시에 존재하면 안 되는 상태
- 구분되지 않고 하나로 처리되는 상태
- 코드상 도달할 수 없는 상태
- 복구할 수 없는 상태
- 앱 재시작 후 유실되는 상태
- 서버와 클라이언트가 서로 다르게 인식할 수 있는 상태

---

# 3. 네트워크 및 통신 예외

기능에 네트워크 요청이 존재한다면 최소한 다음 상황을 검증하세요.

- 요청 전 네트워크 단절
- 요청 직후 네트워크 단절
- 요청 도중 네트워크 단절
- 응답 직전 네트워크 단절
- 서버에서는 성공했지만 클라이언트가 응답을 받지 못한 경우
- Wi-Fi ↔ LTE/5G 전환
- 불안정한 네트워크
- 매우 느린 네트워크
- timeout
- DNS/연결 실패
- 서버 4xx
- 서버 5xx
- 예상하지 못한 response
- 빈 response
- malformed data
- 일부 데이터만 반환
- 동일 요청 재시도
- retry 중 다시 실패
- offline → online 복귀

특히 다음 상황을 중요하게 검증하세요.

> 서버에서는 작업이 성공했지만 클라이언트는 실패했다고 판단하는 상황

중복 요청이나 데이터 불일치가 발생할 수 있는지 확인합니다.

---

# 4. 사용자의 변칙적인 행동

실제 사용자는 개발자가 예상한 순서대로 행동하지 않습니다.

다음을 적극적으로 테스트하세요.

- 버튼 빠르게 연타
- 서로 다른 버튼을 동시에 연속 클릭
- 요청 중 뒤로가기
- 요청 중 화면 닫기
- 요청 중 다른 화면 이동
- 요청 중 앱 background 이동
- 처리 도중 앱 강제 종료
- 완료 직후 앱 강제 종료
- 화면 빠르게 진입/이탈 반복
- 동일 화면 여러 번 진입
- 로딩 중 동일 작업 재실행
- 완료된 작업 다시 실행
- 실패 직후 즉시 재시도
- 여러 번 연속 실패 후 재시도
- 입력 중 화면 이동
- 오래 방치한 화면에서 다시 작업
- 이전 화면으로 이동했다가 재진입
- 앱을 장시간 background에 둔 뒤 복귀

다음 문제가 발생하는지 집중적으로 확인합니다.

- 중복 요청
- 중복 데이터 생성
- Race Condition
- stale state
- 잘못된 화면 이동
- 무한 로딩
- 버튼 영구 비활성화
- 동일 UI 중복 표시
- 이미 unmount된 컴포넌트 업데이트
- 이전 요청이 새로운 요청 결과를 덮어쓰기
- 사용자가 의도하지 않은 작업 실행

# 5. 앱 생명주기

모바일 앱이라면 다음을 반드시 확인하세요.

- foreground → background
- background → foreground
- 앱 강제 종료
- 앱 재실행
- 기기 잠금
- 기기 잠금 해제
- 장시간 background
- OS에 의해 앱 프로세스 종료
- 기기 재부팅
- 앱 업데이트 후 최초 실행

각 상황에서 진행 중이던 작업이 어떻게 되는지 확인하세요.

특히:

> 외부 시스템에서는 작업이 완료되었지만 앱이 완료 사실을 저장하기 전에 종료되는 상황

을 반드시 검증하세요.

앱 재실행 시 정상적으로 상태를 복구할 수 있어야 합니다.

# 6. 상태 관리 및 데이터 정합성

해당 기능이 사용하는 상태 관리 방식을 확인하고 다음을 테스트하세요.

- 초기 상태
- 아직 서버 상태를 모르는 상태
- loading
- success
- failure
- retry
- 캐시 존재
- 캐시 없음
- 오래된 캐시
- 서버와 캐시가 다른 경우
- 전역 상태와 화면 상태가 다른 경우
- 앱 재실행 후 상태
- 로그인/로그아웃 후 상태
- 사용자 변경 후 상태
- background → foreground 후 상태

특히 다음과 같은 구현을 주의해서 확인하세요.

`false`

또는

`null`

같은 단일 값이 실제로는

- 아직 확인하지 않음
- 존재하지 않음
- 요청 실패
- 로딩 중

등 여러 의미로 사용되고 있지는 않은지 확인합니다.

기능이 사용자 계정과 관련되어 있다면 다음을 테스트하세요.

- 비로그인 사용자
- 로그인 직후
- 로그아웃 직후
- 요청 중 로그아웃
- 다른 사용자로 로그인
- 사용자 A → 로그아웃 → 사용자 B
- 토큰 만료
- refresh 실패
- 세션 만료
- 권한 변경
- 삭제된 계정
- 다른 기기에서 변경된 계정 상태
- 동일 계정의 여러 기기 동시 사용

특히 사용자 A의 데이터나 상태가 사용자 B에게 남는 **계정 간 상태 누출**을 집중적으로 확인하세요.

# 8. 외부 SDK / 외부 서비스

외부 SDK 또는 API를 사용하는 경우 해당 시스템이 항상 정상이라고 가정하지 마세요.

다음을 테스트하세요.

- SDK 초기화 실패
- 초기화 지연
- 외부 서비스 장애
- timeout
- 예상하지 못한 에러
- SDK가 성공을 반환했지만 후속 동기화 실패
- 외부 서비스에서는 성공했지만 앱에서는 실패
- 앱에서는 성공으로 판단했지만 외부 서비스에서는 실패
- 외부에서 상태 변경
- 다른 기기에서 상태 변경
- 외부 서비스 응답 지연
- 앱 실행 중 외부 상태 변경

외부 서비스가 Source of Truth인지, 앱/서버가 Source of Truth인지도 확인하세요.

# 10. 권한 예외

카메라, 사진, 위치, 알림 등 OS 권한을 사용하는 경우:

- 최초 허용
- 최초 거부
- 다시 묻지 않음
- 설정에서 권한 제거
- 앱 실행 중 권한 변경
- 제한된 권한
- 권한 요청 중 앱 background
- 권한 요청 후 앱 종료

를 검증하세요.

권한이 없을 때 앱이 crash하거나 막다른 화면에 도달해서는 안 됩니다.

# 11. UI / UX 에러 처리

모든 실패 시나리오에서 다음을 확인하세요.

- loading이 정상적으로 종료되는가
- 중복 실행이 방지되는가
- 사용자가 실패 이유를 이해할 수 있는가
- 재시도할 수 있는가
- 취소와 실패가 구분되는가
- 사용자의 실수가 시스템 오류처럼 표시되지 않는가
- raw API/SDK error가 그대로 노출되지 않는가
- 성공하지 않은 작업이 성공 UI로 표시되지 않는가
- 성공한 작업이 실패 UI로 표시되지 않는가
- 뒤로가기 이후 이상한 상태가 남지 않는가
- 앱 재실행이 필요한 상황을 최소화했는가

에러 메시지가 필요한 경우 적절한 사용자 문구도 제안하세요.

# 테스트 케이스 출력 형식

각 테스트 케이스는 반드시 다음 형식을 사용하세요.

## `[TEST-ID] 테스트 제목`

**테스트 목적**

어떤 장애 또는 예외 상황을 검증하는 테스트인지 설명합니다.

**전제 조건**

- 필요한 사용자 상태
- 필요한 데이터 상태
- 필요한 네트워크/기기 설정
- 기타 필요한 조건

**테스트 절차**

1. 테스터가 수행할 정확한 행동
2. 다음 행동
3. 다음 행동

**기대 결과**

- 화면에 보여야 하는 상태
- 내부 상태가 어떻게 되어야 하는지
- 서버/외부 시스템 상태가 어떻게 되어야 하는지
- 재시도가 가능한지
- 자동 복구가 필요한지
- 필요한 경우 사용자에게 보여줄 에러 문구

**실패 시 리스크**

실제 프로덕션에서 발생할 수 있는 구체적인 문제를 작성합니다.

예:

- 데이터 중복 생성
- 사용자가 수행한 작업 유실
- 서버와 클라이언트 상태 불일치
- 다른 사용자의 상태 노출
- 무한 로딩
- 앱 재실행 전까지 기능 사용 불가
- 잘못된 성공 처리
- 성공했지만 실패로 표시되어 중복 작업 발생

**현재 구현 상태**

다음 중 하나로 표시하세요.

- `PASS` — 현재 구현에서 충분히 방어됨
- `PARTIAL` — 일부 방어되어 있으나 취약점 존재
- `FAIL` — 현재 구현에서 방어되지 않음
- `UNKNOWN` — 정적 코드 분석만으로 판단 불가

가능하면 판단 근거가 되는 파일, 함수, hook, store 등을 함께 작성하세요.

# 테스트 ID 규칙

기능에 맞춰 다음 prefix를 사용하세요.

- `NET-xxx` — 네트워크
- `RACE-xxx` — 중복 실행 / Race Condition
- `LIFE-xxx` — 앱 생명주기
- `STATE-xxx` — 상태 관리
- `AUTH-xxx` — 인증/계정
- `API-xxx` — API/서버
- `SDK-xxx` — 외부 SDK
- `INPUT-xxx` — 사용자 입력
- `PERM-xxx` — OS 권한
- `SYNC-xxx` — 데이터 동기화
- `CACHE-xxx` — 캐시
- `NAV-xxx` — Navigation
- `TIME-xxx` — 시간 관련
- `UI-xxx` — UI/UX 예외

필요하면 기능 특성에 맞는 prefix를 추가해도 됩니다.

# 우선순위 분류

발견한 문제는 다음 기준으로 분류하세요.

## P0 — 출시 전 반드시 수정

다음과 같은 문제가 발생할 가능성이 있는 경우:

- 사용자 데이터 손실
- 잘못된 데이터 생성/변경
- 계정 간 데이터 누출
- 보안 문제
- 금전적 피해
- 복구 불가능한 상태
- 앱 crash
- 핵심 기능 사용 불가
- 서버에서는 성공했지만 앱이 실패로 판단하여 중복 작업이 발생할 가능성

## P1 — 출시 전 수정 권장

복구 가능하지만 실제 사용자 경험에 큰 영향을 주는 문제:

- 무한 로딩
- 잘못된 에러 처리
- 상태 동기화 실패
- 앱 재실행이 필요한 문제
- 중복 요청
- stale state
- 사용자가 작업 결과를 오해할 가능성

# 핵심 복구 경로 분석

기능 특성에 맞춰 **가장 위험한 복구 실패 시나리오를 최소 3개 이상 직접 도출하세요.**

특히 다음 패턴을 우선적으로 고려합니다.

### 1. 외부 작업 성공 → 클라이언트 응답 수신 실패

실제 작업은 성공했지만 앱이 실패했다고 판단했을 때 어떻게 복구하는지 확인합니다.

### 2. 작업 성공 → 로컬 상태 저장 전 앱 종료

앱을 다시 실행했을 때 실제 상태를 다시 확인하여 복구할 수 있는지 확인합니다.

### 3. 외부 상태 변경 → 클라이언트 stale state

다른 기기, 서버, 외부 서비스 등에서 상태가 변경되었을 때 현재 앱이 언제, 어떻게 이를 다시 동기화하는지 확인합니다.

각 시나리오에 대해:

- 현재 복구 방식
- 복구가 시작되는 시점
- Source of Truth
- 복구 실패 가능성
- 누락된 방어 로직

을 분석하세요.
