# Spec — 관심 전시관 새 전시 알림

## Problem

- 지도 전시관/미술관 바텀시트에는 장소를 지속적으로 관심 등록하는 동작이 없다. 사용자는 좋아하는 장소를 발견해도 이후 새 전시가 추가되었는지 직접 다시 찾아야 한다.
- `museums.id`와 `exhibitions.museum_id` 연결은 존재하지만 사용자별 관심 장소 관계를 저장하는 테이블·스토어·동기화 경로가 없다.
- `profiles.push_token`과 `expo-notifications` 의존성은 존재하지만, 토큰 등록·알림 수신·탭 딥링크 코드는 현재 주석 처리되어 있다. UI 토글만으로는 실제 알림을 받을 수 없다.
- 전시 동기화 스크립트 중 일부는 source별 기존 행을 삭제한 뒤 재삽입한다. 단순히 새 `exhibitions.id`만 기준으로 발송하면 같은 전시가 재동기화될 때 중복 알림이 갈 수 있다.

## Goals

- 지도에서 연 전시관/미술관 바텀시트 헤더의 하트 버튼으로 해당 장소를 관심 등록·해제할 수 있다.
- 관심 상태는 로그인 사용자의 계정에 저장되어 앱 재실행·재로그인 후에도 유지되고, RLS로 본인 데이터만 접근할 수 있다.
- 관심 등록 이후 해당 `museum_id`에 실제 새 전시가 유입되면 그 장소를 관심 등록한 사용자에게 푸시 알림을 한 번만 보낸다.
- 푸시 알림을 탭하면 앱의 해당 전시 상세 화면으로 이동한다.
- 알림 권한 거부, 푸시 토큰 부재, 네트워크 저장 실패가 지도 탐색 자체를 막거나 거짓 관심 상태를 만들지 않도록 처리한다.

## Constraints

- 장소 식별자는 표시 이름이 아니라 Supabase `museums.id` / `VenueGroup.museumId`를 사용한다. 이름은 변경·중복될 수 있다.
- 묶음 장소(`subVenues`)에서는 현재 선택된 `activeVenue`를 관심 등록 대상으로 삼는다. 상위 그룹 이름을 일괄 구독하지 않는다.
- 이 기능은 로그인 계정과 서버 푸시 토큰이 필요한 서버 기반 알림이다. 비로그인 사용자의 하트 탭은 로컬 관심 등록으로 처리하지 않고 로그인 화면으로 연결하며, 로그인 후 원래 지도 맥락으로 돌아올 수 있어야 한다.
- iOS 알림 권한 요청은 하트를 탭하기 전에 선제 실행하지 않는다. 사용자가 관심 등록 의사를 보인 시점에만 시스템 권한을 요청한다.
- 관심 등록 성공과 OS 푸시 권한 허용은 별도 상태다. 권한이 거부되어도 관심 장소 관계는 저장할 수 있으며, 앱은 알림을 받을 수 없음을 명확히 안내한다.
- 기존 전시 동기화 방식의 delete/reinsert에도 동일 전시를 재발송하지 않도록, 발송 멱등 키는 일시적인 row id만 사용하지 않는다. 최소한 `museum_id + 정규화한 title + start_date + end_date + user_id` 조합 또는 이에 준하는 안정 키를 서버에서 유일하게 보장한다.
- 관심 등록 이전부터 존재한 진행 중·예정 전시는 소급 발송하지 않는다. 등록 이후 데이터 파이프라인에서 처음 확인된 전시만 대상이다.
- 실제 푸시 발송과 서비스 역할 키 사용은 신뢰 가능한 서버/Edge Function/DB 작업에서 수행한다. 서비스 역할 키를 앱 번들에 포함하지 않는다.
- 기존 `푸시 알림` 설정이 꺼져 있으면 관심 장소 관계는 유지하되 발송 대상에서 제외한다. 설정을 다시 켜도 꺼져 있던 기간의 알림은 소급 발송하지 않는다.

## Non-goals (out of scope)

- 알림 센터 전체 구현(공지, 스크랩 전시 마감, 관람 후 다이어리 유도, 유사 전시 추천) 및 읽음/안 읽음 상태.
- 관심 장소 목록을 별도 화면에서 조회·검색·정렬하는 기능.
- 이메일·문자·카카오톡 알림 또는 장소별 알림 빈도/시간 설정.
- 새 전시 외 휴관, 운영 시간, 티켓 오픈, 전시 종료 임박 알림.
- 기존 장소 좋아요 수 공개, 인기 장소 랭킹, 사용자 간 팔로우/커뮤니티 기능.
- 상위 그룹 하나를 누르면 모든 하위 전시관을 자동 관심 등록하는 기능.
- 과거 전시의 소급 알림 및 이미 발송한 푸시의 회수.

## Users & context

- 사용자는 지도 탭에서 마커를 눌러 `VenueSheet`를 열고 장소 정보와 진행 중/예정 전시를 살펴본다.
- 좋아하는 장소의 새 전시를 놓치고 싶지 않을 때 헤더의 하트 버튼을 누른다.
- 관심 등록 후 앱을 닫아 둔 동안 새 전시가 데이터 동기화로 추가되어도 푸시를 받고, 푸시를 탭해 바로 전시 상세로 이동한다.
- 묶음 장소에서는 하위 장소 칩을 바꾸며 각각의 관심 상태를 독립적으로 설정할 수 있다.

## Acceptance criteria

### AC-1: 바텀시트에서 관심 장소 상태 확인

- **Given** 로그인 사용자가 지도에서 `museumId`가 있는 일반 장소 또는 묶음 장소의 하위 장소를 선택해 바텀시트를 열었고
- **When** 헤더가 렌더되거나 하위 장소 선택이 바뀌면
- **Then** 현재 `activeVenue.museumId`의 서버 관심 상태에 맞춰 최소 44×44pt 터치 영역의 하트 버튼이 비관심(outline) 또는 관심(filled) 상태로 표시되고, `accessibilityRole="button"`, 상태를 포함한 `accessibilityLabel`, `accessibilityState.checked`를 제공한다.

### AC-2: 장소 관심 등록

- **Given** 로그인 사용자가 비관심 상태의 장소 하트를 눌렀고 해당 장소에 유효한 `museumId`가 있으며
- **When** 관심 등록 요청이 성공하면
- **Then** `(user_id, museum_id)` 관계가 서버에 중복 없이 1건 저장되고 하트가 filled 상태로 바뀌며, 앱 재실행 또는 재로그인 후에도 같은 상태가 복원된다.

### AC-3: 비로그인 및 알림 권한 처리

- **Given** 비로그인 사용자 또는 OS 푸시 권한이 아직 결정되지 않은 로그인 사용자가 비관심 하트를 눌렀고
- **When** 사용자가 관심 등록을 시도하면
- **Then** 비로그인 사용자는 로그인 화면으로 이동하고 성공 후 지도 맥락으로 복귀하며, 로그인 사용자는 이 동작의 목적을 설명한 뒤 OS 알림 권한을 요청한다. 권한을 거부해도 관심 등록은 유지하되 푸시를 받을 수 없다는 안내와 시스템 설정 이동 수단을 제공한다.

### AC-4: 장소 관심 해제 및 실패 복구

- **Given** 사용자가 관심 상태의 장소 하트를 누르거나 등록/해제 중 네트워크·서버 오류가 발생하고
- **When** 해제 요청이 성공하면 해당 `(user_id, museum_id)` 관계가 삭제되어 outline으로 바뀌며, 요청이 실패하면 서버 정본 상태로 롤백되고 재시도 가능한 오류 안내가 표시된다
- **Then** 중복 탭은 진행 중 비활성화되어 중복 행·경합을 만들지 않고, 관심 해제 후 발견된 새 전시에 대해서는 알림이 생성·발송되지 않는다.

### AC-5: 푸시 토큰 등록과 전역 설정 준수

- **Given** 로그인 사용자가 OS 알림 권한을 허용했고 앱의 `푸시 알림` 설정도 켜져 있으며 실제 기기에서 앱을 실행했고
- **When** 토큰을 최초 발급하거나 토큰이 갱신되면
- **Then** 유효한 Expo push token이 해당 사용자 프로필에 저장되고, 로그아웃 시 다른 계정으로 토큰이 잘못 연결되지 않는다. OS 권한 또는 앱 설정이 꺼져 있거나 시뮬레이터인 경우 토큰 발급 실패를 크래시로 처리하지 않으며 발송 대상에서 제외한다.

### AC-6: 새 전시 감지와 단일 발송

- **Given** 사용자 A가 시간 T에 `museum_id=M`을 관심 등록했고 푸시 수신 조건을 충족하며
- **When** T 이후 동기화에서 M에 연결된 새 전시 E가 처음 확인되면
- **Then** 서버가 A에게 장소명과 전시명을 포함한 푸시를 정확히 한 번 생성·발송하고 `exhibitionId`와 `museumId`를 payload에 포함한다. 동일 E의 재동기화·함수 재시도·중복 이벤트는 안정 멱등 키로 재발송하지 않으며, T 이전부터 존재한 전시는 보내지 않는다.

### AC-7: 다중 사용자 및 권한 격리

- **Given** 같은 장소를 관심 등록한 사용자, 관심 등록하지 않은 사용자, 등록했다가 해제한 사용자가 함께 있고
- **When** 그 장소에 새 전시가 추가되면
- **Then** 이벤트 시점에 관심 상태이고 수신 조건을 충족한 사용자에게만 각 1회 발송되며, 클라이언트는 RLS에 의해 다른 사용자의 관심 장소·푸시 토큰·발송 이력을 읽거나 변경할 수 없다.

### AC-8: 알림 탭 딥링크와 예외 경로

- **Given** 사용자가 관심 장소의 새 전시 푸시를 받았고
- **When** 알림을 탭하면
- **Then** 앱의 foreground/background/종료 상태 모두에서 payload의 전시 상세 `/(explore)/[id]`로 이동한다. 전시가 삭제되었거나 payload가 유효하지 않으면 크래시하지 않고 전시 탐색 기본 화면으로 이동한다.

### AC-9: 장소 식별자 부재 및 묶음 장소 동작

- **Given** 바텀시트의 현재 장소에 `museumId`가 없거나 사용자가 묶음 장소의 하위 장소를 전환하고
- **When** 헤더의 관심 UI가 갱신되면
- **Then** `museumId`가 없는 장소에서는 하트를 비활성화하고 이유를 접근성 힌트와 사용자 안내로 제공하며 이름 기반 임시 구독을 만들지 않는다. 하위 장소 전환 시에는 각 `activeVenue.museumId`에 대응하는 독립된 하트 상태가 즉시 표시된다.

## Risks & dependencies

- **[P0] 원격 DB 마이그레이션 필요:** 사용자-장소 관계 테이블(예: `followed_museums`)과 RLS, `(user_id, museum_id)` unique/FK가 필요하다. 마이그레이션이 배포되지 않으면 저장·복원이 동작하지 않는다.
- **[P0] 서버 발송 경로 필요:** 새 전시 감지, 관심 사용자 조회, Expo Push API 호출, 발송 멱등 기록을 신뢰 가능한 서버 환경에서 구현해야 한다. 동기화 스크립트가 여러 개이고 delete/reinsert를 사용하므로 모든 sync 완료 후 공통 dispatch 단계를 호출하거나 DB 이벤트를 일관되게 처리해야 한다.
- **[P0] APNs/Expo 자격증명 및 실기기 필요:** 시뮬레이터만으로 실제 iOS 원격 푸시 수신을 검증할 수 없다. Expo projectId와 APNs 설정이 유효해야 하며, 없으면 코드는 완성돼도 AC-5·6·8 실수신 검증은 구조적으로 차단된다.
- **[P0] 전시 식별 안정성:** `sync_kcisa_moca_exhibitions.py` 등은 source 행을 삭제 후 재삽입하므로 row id만으로 멱등성을 보장하면 중복 발송한다. 전시 자연 키 또는 별도 stable key와 DB unique constraint가 필요하다.
- **[P1] 연결 시점:** 새 전시 row가 삽입될 때 `museum_id`가 아직 null이고 이후 `ensure_museums`에서 연결될 수 있다. 알림 감지는 장소 연결 완료 후 수행되어야 누락되지 않는다.
- **[P1] 단일 push token 컬럼:** 현재 `profiles.push_token` 하나는 다중 기기·토큰 회전·로그아웃 처리가 취약하다. MVP에서 단일 기기 정책을 명시적으로 유지하거나 device-token 테이블로 분리해야 한다. 어느 쪽이든 사용자 간 토큰 누출 방지 테스트가 필요하다.
- **[P1] 관심 저장과 권한은 별개:** OS 권한 거부를 관심 저장 실패처럼 보이면 사용자 기대와 서버 상태가 어긋난다. UI와 테스트에서 두 상태를 분리해야 한다.
- Supabase 마이그레이션 후 `src/types/database.types.ts`를 재생성하거나 동일 스키마로 갱신해야 TypeScript 쿼리가 안전하다.
- 새 네이티브 패키지를 추가하는 기능은 아니지만, 현재 주석 처리된 `expo-notifications`를 실제 활성화하므로 기존 개발 클라이언트에 모듈이 포함되어 있는지 확인하고 필요하면 pod install 및 `npx expo run:ios` 리빌드가 필요하다.

2. **AC-1 / AC-2 / AC-3 / AC-4 / AC-9 — 바텀시트 UI:** `activeVenue.museumId` 기반 하트, 44pt 터치 영역, 접근성, 요청 중 잠금, 실패 롤백, 로그인/권한 안내를 구현한다.
3. **AC-5 — 푸시 등록:** 실제 기기 권한 요청, Expo token 저장·갱신, 설정 토글 및 로그아웃/계정 전환 안전성을 연결한다.
4. **AC-6 / AC-7 — 감지·발송 백엔드:** 장소 연결이 완료된 새 전시를 판별하고 관심 사용자만 조회해 멱등 발송하며 성공/실패를 기록한다. 모든 전시 sync 경로가 공통 dispatch를 거치게 한다.
5. **AC-8 — 딥링크:** 알림 payload 검증, 전시 상세 이동, 삭제/오염 payload fallback을 앱 세 상태에서 구현한다.
6. **AC별 Taylor 전체 체크:** tsc, 테스트, 바텀시트 스크린샷 직접 확인, 일반/묶음 장소 토글, 로그인 복귀, 관심 복원·해제·실패 롤백, 인접 지도/전시 상세 회귀를 매 AC마다 처음부터 실행한다. 실제 푸시는 자격증명이 준비된 실기기에서 발송 1회·재처리 0회·딥링크를 검증한다.
