# Spec — 감상 에세이 생성 (확정 큐 통합, rev2 — 한줄평/감상문 통합)

## Problem

- rev1에서는 "한줄평"(짧은 텍스트 입력)과 "감상문"(AI 생성, 별도 3단계 읽기전용 화면)을 서로 다른 개념으로 분리해 구현·QA까지 완료했다. 그런데 실사용 피드백에서 이 분리가 어색하다는 지적을 받았다 — 사실상 같은 자리(그날의 감상을 남기는 자리)인데 입력칸이 두 번 나오고, 생성된 감상문은 읽기 전용이라 손으로 다듬을 수 없었다.
- 확정 큐 흐름이 "별점 → 한줄평 → 감상 생성 단계(별도 화면 성격) → 서명"으로 4단계가 되어, 단순한 관람 기록 확정치고 단계가 많고 개념적으로 중복된 입력을 두 번 요구한다.
- (참고: 이 SPEC은 rev1 구현·QA 완료 이후 사용자 피드백을 반영한 재설계다. "한줄평"과 "감상문 생성"을 하나의 입력 경험("감상평")으로 합치는 방향은 이미 사용자와의 대화로 확정됐다 — 재논의 대상 아님.)

## Goals

- 기존 "한줄평" 입력칸과 별도 3단계 "감상 생성" 화면을 하나의 "감상평" 입력칸으로 통합한다. 입력칸 라벨은 "감상평"으로 변경한다(AC-1).
- 감상평 입력칸 위(또는 옆)에 "직접 쓰기"/"생성하기" 두 가지 작성 방식을 토글로 제공한다(AC-2).
- "생성하기"는 별점 + 그날 들은 해설 목록(+ 이미 입력된 텍스트가 있으면 참고 재료로)을 바탕으로 감상평을 생성한다. 별점만 있고 감상평이 비어 있어도 "생성하기"가 가능해야 한다 — 감상평은 재료를 보강할 뿐, 생성의 필수 조건이 아니다(AC-3, rev1 AC-1 취지 계승).
- 생성 결과는 별도의 읽기 전용 표시 영역이 아니라, 감상평 `TextInput` 그 자체에 실시간 스트리밍으로 채워진다(AC-6).
- 생성 중에는 입력칸을 잠가(`editable=false`) 사용자 타이핑과 스트리밍 델타가 충돌하지 않게 하고, 스트리밍 완료 후 다시 편집 가능하게 푼다(AC-5, AC-7).
- 생성이 완료된 뒤에도 사용자가 결과를 자유롭게 수정할 수 있다 — 일반 `TextInput`과 동일하게 동작한다(AC-7).
- 확정 큐 흐름을 별점(1단계) → 감상평(2단계, 직접 쓰기 또는 생성하기로 채우고 계속 편집 가능) → "완료" → 서명(3단계)으로 단순화한다. 기존의 "감상 생성 단계 진입 → 완료 확인 → 서명하러 가기" 별도 3단계 흐름은 사라진다(AC-11).
- 생성된(또는 직접 쓴) 감상평은 `confirmVisit` 호출 시 관람 기록(Visit)에 저장된다(AC-14).

## Non-goals (out of scope)

- 감상평에 대한 버전 히스토리/되돌리기(undo) — "생성하기"를 다시 누르면 화면상 텍스트는 새 스트리밍 결과로 대체될 뿐, 이전 텍스트로 되돌리는 기능은 범위 밖이다.
- 감상평에 대한 TTS 재생 — 텍스트 생성/편집만 다루며 음성 변환은 하지 않는다(rev1 유지).
- 확정된 과거 관람 기록에 대한 소급 감상평 생성 — 이번 spec은 `confirm-visits` 큐를 진행하는 동안에만 적용되며, 이미 `confirmed` 상태인 기록에 나중에 감상평을 추가/생성하는 기능은 포함하지 않는다(rev1 유지).
- 이미 `confirmed` 상태로 저장된 rev1 기록(`memo`/`essay`가 각각 채워져 있을 수 있는 기존 데이터)의 마이그레이션 — 정확한 처리 방식이 정해지기 전까지는 이번 SPEC 범위 밖이다(Open Questions 참고).
- "직접 쓰기"/"생성하기" 이외의 제3의 입력 방식(예: 음성 입력) — 범위 밖.
- 재생성 횟수 자체를 무제한 허용할지 제한할지는 Open Questions에서 확정 전까지 미정이며, 최종 정책이 정해지기 전까지는 기본값(무제한)으로 간주하지 않는다.

## Users & context

- 오디오가이드 관람을 마치고 확정 큐(`app/diary/confirm-visits.tsx`)에서 별점·감상평·서명을 남겨 관람 기록을 확정하는 사용자.
- 확정 큐는 여러 건의 `pending` 상태 관람을 하나씩 순회하는 구조이므로, 감상평 입력/생성 상태도 각 큐 항목(카드)마다 독립적으로 초기화되어야 한다(rev1과 동일한 전제).

## Acceptance criteria

### AC-1: 입력칸 통합 및 라벨 변경

- **Given** 사용자가 확정 큐에서 별점을 매긴 직후
- **When** 화면이 렌더링되면
- **Then** 기존의 "한줄평" 입력칸과 별도 3단계 "감상 생성" 화면 대신, "감상평"이라는 라벨의 단일 입력칸 하나만 나타난다(정확한 placeholder 문구는 Sam의 `02-design-brief.md`에서 확정)

### AC-2: 두 가지 작성 방식 노출

- **Given** 감상평 입력칸이 나타난 상태
- **When** 화면을 확인하면
- **Then** 입력칸 위(또는 옆)에 "직접 쓰기"와 "생성하기" 두 옵션이 토글 형태로 함께 노출된다

### AC-3: 별점만 있어도 "생성하기" 가능

- **Given** 별점만 매기고 감상평 입력칸이 빈 상태일 때
- **When** "생성하기"를 누르면
- **Then** 별점 + 그날 들은 해설 제목 목록 + 전시명만 재료로 감상평 생성 요청이 시작된다(버튼이 비활성화되지 않는다)

### AC-4: 기존 입력 텍스트를 참고 재료로 포함

- **Given** 사용자가 "직접 쓰기"로 이미 일부 텍스트를 입력했거나 이전에 생성된 텍스트가 남아있는 상태일 때
- **When** "생성하기"를 누르면
- **Then** 별점 + 들은 해설 목록 + 전시명에 더해, 입력칸에 있던 기존 텍스트도 참고 재료로 포함되어 생성 요청이 시작된다

### AC-5: 생성 중 입력칸 잠금

- **Given** "생성하기"를 눌러 감상평 생성 요청이 진행 중일 때
- **When** 스트리밍 응답을 수신하는 동안
- **Then** 감상평 입력칸은 편집 불가능(`editable={false}`) 상태가 되어 사용자 타이핑과 스트리밍 델타가 충돌하지 않는다

### AC-6: 생성 결과가 입력칸에 실시간 스트리밍으로 표시

- **Given** 감상평 생성 요청이 진행 중일 때
- **When** `stream-chat` 응답이 SSE 델타로 도착하면
- **Then** 별도의 읽기 전용 영역이 아니라 감상평 `TextInput`의 값 자체가 점진적으로("주루루룩") 채워진다

### AC-7: 생성 완료 후 자유 편집 가능

- **Given** 감상평 스트리밍이 끝까지 도착해 생성이 완료된 상태
- **When** 화면을 확인하면
- **Then** 입력칸의 잠금이 풀려(`editable={true}`) 사용자가 생성된 감상평을 일반 텍스트 입력처럼 자유롭게 수정할 수 있다

### AC-8: 감상평 없이도 다음 단계 진행 가능

- **Given** 별점만 매기고 감상평 입력칸을 빈 상태로 둔 채(직접 쓰기도, 생성하기도 하지 않고)
- **When** 완료 액션(AC-11)을 실행하면
- **Then** 감상평이 비어있는 채로 서명 단계로 진입한다 — 감상평은 서명 진행의 필수 조건이 아니다

### AC-9: 들은 해설이 없는 경우

- **Given** 그날 들은 해설이 하나도 없는 관람 기록(`listenedTitles`가 빈 배열)일 때
- **When** "생성하기"를 누르면
- **Then** 별점(+기존 입력 텍스트가 있으면 그것)만 재료로 감상평 생성이 진행된다(버튼 자체가 비활성화되지 않는다)

### AC-10: 생성 실패 처리

- **Given** 감상평 생성 요청 중 네트워크 오류 또는 `stream-chat` 서버 오류가 발생했을 때
- **When** 스트리밍 응답을 받는 데 실패하면
- **Then** 입력칸의 잠금이 풀리고 오류 상태가 화면에 표시되며, 사용자는 재시도하거나 입력칸에 직접 텍스트를 쓰는 것 중 하나를 선택할 수 있다

### AC-11: 완료 액션으로 서명 단계 진입

- **Given** 별점을 매긴 뒤 감상평 입력칸이 나타난 상태(생성 중이 아님)
- **When** 감상평 입력칸에서 키보드 "완료" 키(`onSubmitEditing`)를 누르거나, 감상평 섹션 하단에 노출되는 명시적 "다음"(또는 동일 의도의) 버튼을 누르면
- **Then** 두 액션 중 어느 쪽을 사용하든 동일하게 서명 단계로 진입한다 — 생성 완료만으로 자동 진행되지 않는다(정확한 버튼 문구/배치는 Sam의 `02-design-brief.md`에서 확정)

### AC-12: 생성 중에는 다음 단계 진행 차단

- **Given** 감상평 생성 요청이 진행 중일 때(스트리밍 중)
- **When** 사용자가 완료 액션(AC-11의 키보드 완료 또는 "다음" 버튼)을 시도하면
- **Then** 서명 단계로 진행되지 않는다 — 완료 액션은 생성이 끝나거나(또는 애초에 생성을 시작하지 않은 상태에서)만 유효하다

### AC-13: 화면 이탈 시 처리

- **Given** 감상평 생성이 진행 중인 상태에서 사용자가 화면을 벗어나면(뒤로가기 등)
- **When** 컴포넌트가 언마운트되면
- **Then** 진행 중이던 생성 요청은 취소되고 미완성 감상평은 폐기된다(rev1의 `beforeRemove`/언마운트 정리 패턴 재사용)

### AC-14: 감상평 저장

- **Given** 감상평 입력칸에 텍스트가 있는(직접 썼든, 생성 후 그대로 두었든, 생성 후 수정했든 상관없이) 상태에서 사용자가 서명을 완료하고 관람 기록을 확정할 때
- **When** `confirmVisit`이 호출되면
- **Then** 입력칸에 현재 표시된 감상평 텍스트가 해당 관람 기록(Visit)의 저장 대상 필드에 저장된다. 감상평이 비어있었다면(AC-8) 빈 문자열로 저장되고, 기존 별점/서명 저장 동작에는 변화가 없다

## Risks & dependencies

- **`DayVisit.memo`/`essay` 필드 통합**: rev1은 "한줄평"(`memo`)과 "감상문"(`essay`)을 별개 필드로 저장했다. 입력칸이 하나로 합쳐지는 이번 설계에서는 데이터도 `memo` 필드 하나로 합치고 `essay` 필드는 제거하는 방향을 권장한다(중복 방지, `confirmVisit`/`setVisitMemo` 시그니처 단순화). 다만 이미 `confirmed` 상태로 저장된 rev1 사용자 기록에는 `memo`와 `essay`가 서로 다른 내용으로 채워져 있을 수 있어, 필드 제거 시 기존 데이터를 어떻게 처리할지는 결정되지 않았다 — Open Questions #1 참고. 확정 전까지는 `essay` 필드를 코드에서 완전히 제거하지 않는다.
- **스트리밍 값을 controlled `TextInput`에 바인딩**: 기존 `useDescriptionStream`/`useEssayStream` 패턴은 25ms 간격 문자 단위 델타를 읽기 전용 `Text` 컴포넌트에 렌더링하는 용도로만 검증됐다. 이번 spec은 동일한 스트리밍 값을 controlled `TextInput`의 `value`에 바인딩하는 새로운 사용처다 — 스트리밍 중에는 입력칸이 포커스를 잃은(잠금) 상태라 커서 점프 문제는 없을 것으로 예상되지만, Chris 구현 시 시뮬레이터로 실제 확인이 필요하다.
- **잠금/해제 타이밍 동기화**: `editable` 상태는 반드시 `useEssayStream`의 `stage`(`streaming`/`done`) 값을 단일 소스로 삼아야 한다 — 별도 boolean 상태로 중복 관리하면 스트리밍 마지막 델타 직후 짧은 시간 동안 잠금/해제가 어긋나 편집과 델타가 충돌할 수 있다.
- **"생성하기" 재실행 시 기존 텍스트 덮어쓰기**: 사용자가 직접 쓴(또는 이전에 생성된) 텍스트가 있는 상태에서 "생성하기"를 다시 누르면, 화면상 텍스트는 새 스트리밍 결과로 대체된다(참고 재료로는 쓰이지만 원문은 사라짐) — 공들여 쓴 텍스트가 예고 없이 사라질 수 있다. 확인 다이얼로그가 필요한지는 Open Questions #2 참고.
- **`ReceiptSummary.tsx` 복잡도**: 이미 별점/한줄평/서명 상태(스크롤 잠금, 키보드 포커스, 서명 패드 제스처)가 얽혀 있는 컴포넌트에 작성 방식 토글 + 잠금 로직까지 더해진다. `component-convention.md` §9.4의 분리 신호(100줄 초과 + UI 블록 2개 이상)에 해당할 가능성이 높으므로 서브컴포넌트 분리를 적극 검토해야 한다(단, `EssayStageSection.tsx` 자체는 rev1과 같은 "별도 3단계" 개념이 아니라 "감상평 섹션" 서브컴포넌트로 새로 설계되어야 한다).
- **`onMemoDone`/`essayStageReady` 등 rev1 상태·prop 명칭의 의미 변화**: rev1은 "메모칸 완료 = 감상 생성 단계 진입"이라는 2단계 개념으로 명명되어 있었다. 통합 이후에는 "감상평 입력 완료 = 서명 진입"이라는 단일 개념이므로, 관련 prop/상태 변수명을 그대로 재사용하면 오해를 부를 수 있어 개명을 권장한다(정확한 이름은 Chris 구현 판단).
- `stream-chat` Edge Function은 `requireUser`로 인증을 요구한다 — 확정 큐 자체가 로그인 사용자 전용 플로우이므로 비로그인 분기 처리는 불필요하다(rev1에서 이미 확인됨, moot).

## Open questions — 확정 (2026-09-12, 사용자 결정)

- **기존 confirmed 기록 마이그레이션** → **`memo`가 비어있으면 `essay`를 `memo`로 이관, 둘 다 값이 있으면 `memo` 우선(`essay`는 버림).** 병합(concat)하지 않는다.
- **"생성하기" 덮어쓰기 확인** → **조용히 대체.** 확인 다이얼로그 없이 바로 새 스트리밍 결과로 교체한다.
- **재생성 횟수 제한** → **최대 5회.** 정상 재생성("생성하기" 재클릭)에 상한을 적용한다. 오류 시 재시도(`MAX_ESSAY_RETRIES`)와 별개 카운터로 관리할지 통합할지는 Chris 구현 판단(권장: 하나의 카드 세션 동안 "생성하기" 버튼을 누른 총 횟수를 5회로 제한하는 단일 카운터 — 정상 재생성과 오류 재시도를 구분하지 않는 편이 단순함).
- **토글 기본 선택 상태** → **"직접 쓰기" 기본 + 자동 포커스.** rev1의 `hasFocusedMemoRef` 패턴(별점을 처음 매긴 순간에만 자동 포커스)을 그대로 유지한다.

### AC-15: 재생성 횟수 상한

- **Given** 한 카드 세션에서 "생성하기"를 이미 5회 누른 상태
- **When** "생성하기"를 다시 누르면
- **Then** 생성 요청이 시작되지 않고, 버튼이 비활성화되거나 상한 도달 안내가 표시된다(정확한 UI는 Sam의 `02-design-brief.md`에서 확정)
