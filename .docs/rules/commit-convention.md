# Commit Convention

## 형식

```
type(scope): 한글 텍스트
```

type, scope, text 세 항목 모두 필수입니다.

## Type

| type       | 용도                              |
| ---------- | --------------------------------- |
| `feat`     | 새 기능                           |
| `fix`      | 버그 수정                         |
| `chore`    | 빌드·설정·의존성 등 기능 외 작업  |
| `refactor` | 동작 변경 없는 코드 개선          |
| `style`    | 포맷·공백·세미콜론 등 코드 스타일 |
| `docs`     | 문서 작성·수정                    |
| `perf`     | 성능 개선                         |
| `test`     | 테스트 추가·수정                  |
| `build`    | 빌드 시스템·CI 변경               |

## Scope

프로젝트 주요 도메인 단위로만 사용합니다. 세부 파일명은 쓰지 않습니다.

| scope      | 대상                                   |
| ---------- | -------------------------------------- |
| `app`      | 화면·라우팅 (`app/`)                   |
| `api`      | API 클라이언트 (`src/utils/api.ts`)    |
| `ui`       | 컴포넌트·레이아웃 (`src/components/`)  |
| `store`    | 상태 관리 (`src/store/`)               |
| `tts`      | TTS·오디오 (`src/hooks/useTTS.ts`)     |
| `supabase` | Edge Functions (`supabase/functions/`) |
| `deps`     | 의존성 추가·제거·업데이트              |
| `config`   | 설정 파일 (env, tsconfig, tailwind 등) |

## Text 규칙

- **한글**로 작성
- 명령형 동사로 끝내기: `~추가`, `~수정`, `~제거`, `~개선`
- 마침표 없음

## 올바른 예시

```
feat(app): 검색 화면 추가
fix(api): 스트리밍 응답 파싱 오류 수정
chore(deps): expo-file-system 설치
refactor(store): chatStore 액션 단순화
style(ui): ScreenHeader 들여쓰기 정리
docs(config): 환경 변수 설명 추가
```

## 잘못된 예시

```
fix: 버그 수정            # scope 없음 → FAIL
feat(screens): 추가       # 허용되지 않는 scope → FAIL
fix(ui) 버튼 수정         # 콜론 없음 → FAIL
```

## 설정 파일

- `commitlint.config.js` — 형식 강제 (husky commit-msg 훅)
- `.husky/commit-msg` — commitlint 실행 훅

## 커밋 전 검증 절차

큰 변경이나 여러 파일을 묶어 커밋할 때는 바로 커밋하지 않고 아래 루프를 거친다.

1. **그룹핑**: 워킹트리 변경을 논리적 단위(기능·도메인)로 나눈다. 무관한 변경을 한 커밋에 묶지 않는다 — 여러 단위가 섞여 있으면 단위별로 이 절차 전체를 따로 돌린다.
2. **스테이징**: 그 그룹에 속한 파일만 `git add`로 스테이징한다.
3. **포맷 확인**: `npm run format:check`를 실행한다. 실패하면 변경 그룹 안의 파일만 포맷하고 다시 스테이징한다.
4. **린트 확인**: `npm run lint`를 실행한다. 새 오류·경고가 이번 그룹에서 생겼으면 수정하고 다시 스테이징한다. 기존 무관 경고는 기록만 한다.
5. **타입 체크**: `npx tsc --noEmit`을 실행한다. 이번 그룹에서 생긴 타입 오류만 수정하고 다시 스테이징한다.
6. **테스트**: `npm test`를 실행한다. 실패가 이번 그룹 때문이면 수정하고 다시 스테이징한다. 무관한 기존 실패는 보고만 한다.
7. **컨벤션 대조**: 스테이징된 diff가 `.docs/rules/component-convention.md`, `.docs/rules/feature-pipeline.md`, 이 문서의 커밋 메시지 규칙을 위반하지 않는지 직접 확인한다.
8. **리뷰**: 스테이징된 diff를 직접 읽어 1차 리뷰하고, `/moai:review`로 2차 검토해 버그·회귀 가능성을 확인한다.
9. **버그 수정**: 직접 리뷰, `/moai:review`, format/lint/tsc/test, 컨벤션 대조 중 하나라도 문제가 있으면 수정하고 다시 스테이징한다.
10. **반복**: 문제가 없어질 때까지 3~9번을 반복한다.
11. **커밋**: 모든 검증과 리뷰를 통과하면 위 커밋 컨벤션(type(scope): 한글 텍스트)에 맞춰 커밋한다. 남은 그룹이 있으면 1번으로 돌아간다.

### 에러 핸들링

- 리뷰 중 발견한 문제가 이번 diff의 의도인지 실수인지 애매하면 임의로 고치거나 넘기지 않고 사용자에게 확인한다.
- format/lint/tsc/test가 그룹 무관하게 이미 깨져 있었다면 이번 스테이징 탓인지 먼저 구분한다. 무관한 기존 실패까지 이 루프에서 고치지 않는다.
- 범위 밖 코드에서 별개의 버그를 발견해도 드라이브바이로 고치지 않는다. 발견 사실만 보고한다.
- 같은 그룹을 3번 이상 수정해도 검증이 통과하지 않으면 멈추고 무엇이 막혔는지 보고한다.
