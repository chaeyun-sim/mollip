## 1. 네트워크 및 통신 예외

[x] NET-01 / 최초 실행부터 오프라인

> - 전제 조건: 상품·구독 캐시가 없는 테스트 설치. 비행기 모드를 켜고
>   Wi-Fi도 끕니다.

> - 테스트 절차: ① 앱 실행 → ② 구독 화면 진입 → ③ 구매 시도 → ④ 네트워
>   크 연결 후 재시도.

> - 기대 결과: “상품 정보를 불러오지 못했어요. 연결 후 다시 시도해 주세
>   요.” 표시. 유효한 상품 없이 구매를 실행하지 않습니다. 연결 복구 후
>   화면을 다시 설치하지 않고 정상화할 수 있습니다.

> - 실패 시 리스크: 무한 로딩, 빈 가격, 임의 가격 노출, 앱 충돌.

[x] NET-02 / 상품 조회 중 연결 단절

> - 전제 조건: 상품 응답을 지연시킬 수 있는 환경.
> - 테스트 절차: ① 구독 화면 진입 → ② 상품 조회 중 네트워크 차단 → ③ 대
>   기 제한 경과 → ④ 연결 복구 후 재조회.

> - 기대 결과: 로딩이 복구 가능한 오류 상태로 전환됩니다. 일부 상품만
>   로드됐다면 없는 상품은 구매할 수 없으며 다른 상품으로 잘못 대체되지
>   않습니다.

> - 실패 시 리스크: 잘못된 상품 구매, 영구 비활성 버튼, 로딩 고착.

[x] NET-03 / 구매 버튼을 누르기 직전 연결 단절

> - 전제 조건: 상품 조회 완료, 미구독 계정.
> - 테스트 절차: ① 상품 선택 → ② 비행기 모드 활성화 → ③ 구매 → ④ 연결
>   복구 → ⑤ 거래 상태 확인.

> - 기대 결과: 오류 또는 확인 대기 상태를 적절하게 안내합니다.

>   과 확인 후 다음 구매를 허용합니다.

> - 실패 시 리스크: 무료 권한 지급, 진행 중 거래의 중복 요청.

[x] NET-04 / Apple 승인 직후 RevenueCat 통신 단절

> - 전제 조건: Apple 통신은 허용하고 RevenueCat 통신만 차단할 수 있는
>   환경.

> - 테스트 절차: ① 구매 인증 진행 → ② 승인 직후 RevenueCat 통신 차단 →

> - 기대 결과: SDK가 유효한 entitlement를 반환하면 반영합니다. 확인되지
>   않았다면 “구매 결과를 확인하고 있어요. 다시 구매하지 말고 잠시 후
>   상태를 확인해 주세요.” 표시. 복구 후 동일 거래의 권한이 정상 반영됩
>   니다.

> - 실패 시 리스크: 결제 후 서비스 미제공, 불필요한 재구매 유도.

> 지원 조건에서는 RevenueCat의 Offline Entitlements가 서버 장애 중에도
> 권한을 반환할 수 있습니다. 따라서 이 케이스의 합격 기준을 무조건 “오

[x] NET-05 / Wi-Fi ↔ LTE·5G 반복 전환

> - 실패 시 리스크: 구매창 중첩, 중복 처리, 성공 후 오류 화면 표시.

[x] NET-06 / 장시간 타임아웃 후 늦은 성공 응답

> - 전제 조건: 구매 결과 전달을 앱의 대기 제한보다 오래 지연.
> - 테스트 절차: ① 구매 → ② 대기 제한 경과 → ③ 화면 닫기 및 재진입 → ④
>   지연된 성공 결과 전달.

> - 기대 결과: 사용자는 대기 화면에서 벗어날 수 있습니다. 결과 미확정
>   상태에서는 무분별한 재구매를 방지하고, 늦은 유효 결과는 정상 반영합
>   니다.

> - 실패 시 리스크: 타임아웃을 취소로 오인, 늦은 성공 누락, 이미 닫힌
>   화면에서 충돌.

[x] NET-07 / 연결 표시는 있지만 인터넷 사용 불가

> - 전제 조건: 로그인 필요한 공용 Wi-Fi, DNS 실패, VPN 차단 환경을 각각
>   준비.

> - 테스트 절차: ① 해당 네트워크 연결 → ② 상품 조회·구매·상태 조회 → ③
>   정상 네트워크로 이동 → ④ 재시도.

> - 기대 결과: 연결 아이콘만으로 통신 성공을 판단하지 않습니다. “인터넷
>   연결을 확인해 주세요.” 안내 후 복구할 수 있고, 원시 서버 응답이나
>   HTML이 화면에 노출되지 않습니다.

> - 실패 시 리스크: 응답 파싱 충돌, 무한 재시도, 내부 오류 노출.

[x] NET-08 / 기존 구독자의 장기 오프라인 사용

> - 전제 조건: 온라인에서 활성 entitlement 확인 완료. 설치 SDK의 캐시
>   정책과 앱의 오프라인 허용 기준 기록.

> - 테스트 절차: ① 오프라인 전환 → ② 재실행 및 유료 기능 접근 → ③ 허용
>   기간 전후 반복 → ④ 온라인 복구.

> - 기대 결과: 정해진 오프라인 정책대로 동작합니다. 단순 조회 오류로 즉
>   시 권한을 제거하거나, Zustand에 저장된 값만으로 무기한 권한을 유지
>   하지 않습니다.

> - 실패 시 리스크: 정상 구독자 차단, 만료 후 무제한 무료 사용.

> 캐시가 반환됐다는 사실과 서버의 최신 상태를 확인했다는 사실은 다릅니
> 다. 오프라인 경계값은 설치 버전에 적용되는 SDK 동작을 기준으로 검증합

## 2. 유저의 변칙적 행동

[x] USR-01 / 구매 버튼 연타

> - 전제 조건: 구매 호출 횟수를 기록할 수 있는 빌드.
> - 테스트 절차: ① 구매 버튼을 1초 내 10회 탭 → ② 첫 처리 중 추가 탭 →
>   ③ 취소 후 다시 구매.

> - 기대 결과: 진행 중 구매 호출은 하나입니다. 버튼 비활성화와 실제 호
>   출 방지가 모두 작동하고, 취소 후에는 정상 재시도가 가능합니다.

> - 실패 시 리스크: 중복 요청, 구매창 중첩, 영구 잠금.

[x] USR-02 / 상품을 빠르게 변경하며 구매

> - 전제 조건: 세 상품 모두 표시.
> - 테스트 절차: ① 1주 선택 → ② 6개월 선택 직후 구매 → ③ 구매 처리 중 1

> - 기대 결과: 구매 시작 시 확정된 상품과 Apple 결제창의 기간·가격이 일
>   치합니다. 진행 중 선택 변경이 기존 요청을 바꾸지 않습니다.

> - 실패 시 리스크: 원치 않은 장기 구독, 가격 오인.

[x] USR-03 / 구매와 복원을 동시에 실행

> - 전제 조건: 구매·복원 버튼 접근 가능.
> - 테스트 절차: ① 구매 직후 복원 탭 → ② 역순으로 반복 → ③ 다른 화면의
>   구매 버튼도 시도.

> - 기대 결과: 충돌하는 작업을 직렬화하거나 명확하게 차단합니다. “구매
>   처리 중이에요.”처럼 현재 작업을 안내하고 종료 후 조작이 복구됩니다.

> - 실패 시 리스크: 상태 경쟁, 권한 덮어쓰기, 처리 중단.

[x] USR-04 / Apple 결제창에서 직접 취소

> - 전제 조건: 미구독 계정.
> - 테스트 절차: ① 결제창 열기 → ② 취소 → ③ 다시 구매 → ④ 다시 취소.

> - 기대 결과: 사용자 취소를 심각한 결제 오류로 표시하지 않습니다. 구독
>   화면으로 정상 복귀하며 권한·성공 이벤트를 생성하지 않습니다.

> - 실패 시 리스크: 취소를 실패로 과대 집계, 불필요한 경고, 다음 구매
>   불가.

[ ] USR-05 / 결제 중 강제 종료

> - 전제 조건: 단계별 거래 기록을 확인할 수 있는 환경.
> - 테스트 절차: 각각 ① 결제창 표시 직후, ② 인증 진행 중, ③ Apple 승인
>   직후에 앱 강제 종료 → ④ 재실행.

> - 기대 결과: 종료 자체로 성공·실패를 단정하지 않습니다. 완료된 거래는
>   재실행 후 반영되고, 완료되지 않은 거래에는 새 권한을 지급하지 않습
>   니다.

> - 실패 시 리스크: 결제 유실, 무료 권한, 영구적인 ‘구매 중’ 상태.

[ ] USR-06 / 홈 이동·화면 잠금·전화 수신 후 복귀

> - 전제 조건: 구매 가능한 실제 기기.
> - 테스트 절차: ① 구매 중 홈 이동 또는 잠금 → ② 잠시 후 복귀 → ③ 인증
>   전후 반복 → ④ 전화 수신으로도 반복.

> - 기대 결과: 복귀 시 상태를 재확인합니다. 결제창이 사라졌다는 이유만
>   으로 취소 처리하지 않으며 로딩·버튼·권한이 일관됩니다.

> - 실패 시 리스크: 백그라운드 거래 누락, 중복 결제창, UI 고착.

[ ] USR-07 / 구매 중 화면 이탈 및 재진입

> - 전제 조건: 뒤로가기·탭 이동·딥링크로 구독 화면 이탈 가능.
> - 테스트 절차: ① 구매 시작 → ② 화면 이탈 → ③ 다른 화면에서 거래 완료

> - 실패 시 리스크: 권한 갱신 누락, 내비게이션 꼬임, 충돌.

[ ] USR-08 / 구매 중 앱 계정 전환

> - 전제 조건: 앱 로그인 기능, 유료 계정 A와 무료 계정 B.
> - 테스트 절차: ① A로 구매 또는 상태 조회 시작 → ② 로그아웃·B 로그인

> - 실패 시 리스크: 다른 계정으로 권한 유출, 구매 소유자 불일치.

## 3. Apple·RevenueCat 서버 및 계정 상태 예외

[ ] ACC-01 / Ask to Buy 승인 대기

> - 전제 조건: Xcode StoreKit의 Ask to Buy 테스트 환경.
> - 테스트 절차: ① 구매 요청 → ② 승인하지 않고 대기 → ③ 화면 이동 → ④
>   앱 재실행.

> - 기대 결과: “구매 승인을 기다리고 있어요. 승인되면 구독 상태가 반영
>   됩니다.” 안내. 새 권한을 선지급하지 않고 다른 앱 기능은 사용할 수
>   있습니다.

> - 실패 시 리스크: 승인 전 무료 사용, 무한 로딩, 반복 승인 요청.

[ ] ACC-02 / 승인 대기 후 승인·거절

> - 전제 조건: ACC-01 상태.
> - 테스트 절차: ① 앱 실행 중 승인 → ② 별도 거래에서는 종료 중 승인 후
>   재실행 → ③ 또 다른 거래는 거절.

> - 기대 결과: 승인된 거래는 재구매 없이 반영됩니다. 거절에는 새 권한을
>   지급하지 않습니다. 거절 콜백 제공 여부와 관계없이 앱이 영구 잠금되
>   지 않습니다.

> - 실패 시 리스크: 승인됐지만 이용 불가, 거절 후 대기 상태 고착.

> Ask to Buy는 Xcode에서 승인·거절을 재현할 수 있습니다. RevenueCat의
> pending 오류는 일반적인 결제 실패와 구분해야 합니다. Apple Ask to Buy
> 테스트, RevenueCat 오류 처리

[ ] ACC-03 / 카드 한도 초과·결제 수단 거절

> - 전제 조건: Sandbox에서 구매 실패 설정. 카드별 세부 사유는 오류 주입
>   으로 보완.

> - 테스트 절차: ① 신규 구매 실패 유도 → ② 실패 후 재시도 → ③ 실패 조건
>   해제 후 구매.

> - 기대 결과: “결제를 완료하지 못했어요. App Store의 결제 수단을 확인
>   해 주세요.” 안내. SDK가 전달하지 않은 사유를 ‘한도 초과’ 등으로 단
>   정하지 않습니다.

> - 실패 시 리스크: 실패 거래에 권한 지급, 잘못된 원인 안내, 복구 불가.

[ ] ACC-04 / 구매 제한·Apple 로그인 취소

> - 전제 조건: 스크린 타임 구매 제한 환경 및 Apple 인증이 필요한 환경.
> - 테스트 절차: ① 제한 상태에서 구매 → ② 제한 해제 후 재시도 → ③ Apple
